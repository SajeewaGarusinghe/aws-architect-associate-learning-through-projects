The instinct when a site will not load from S3 is to make the bucket public. That instinct is the source of a large share of real-world data exposure. This lab builds the same outcome with the bucket fully locked down, and the mechanism that makes it work — Origin Access Control — is a recurring exam topic.

Scope In scope: Origin Access Control, bucket policies as the grant mechanism, cache behaviours and invalidation, S3 storage classes and lifecycle transitions, and versioning. Out of scope: custom domains and ACM certificates, Lambda@Edge, and signed URLs.

Reference architecture

01. Locked down and globally served
In one line

"Public" is not a property of the bucket — it is a question of which principal the bucket policy names, and here the only principal named is one specific CloudFront distribution, which signs every origin request with SigV4 to prove it.

Context & requirements

What it must do

  • Serve a website over HTTPS worldwide
  • Cache at the edge, close to viewers
  • Recover an object overwritten by mistake
  • Move cold data to cheaper storage on a schedule

How it must behave

  • All four public-access blocks on, permanently
  • Direct S3 URLs must return AccessDenied
  • Only this distribution may read the bucket
  • HTTP redirected to HTTPS

Constraints

  • No ACM certificate, no domain to own
  • No EC2, no VPC
  • Idle cost zero
  • Distribution deploys in 3–5 minutes
High-level design
S3 bucket
All four public-access blocks enabled, encrypted, versioned. Why: the blocks are a backstop that overrides any future policy or ACL mistake — even an explicitly public policy would be refused while they are on.
Origin Access Control
Signs every origin request with SigV4. Why: OAC replaces the older Origin Access Identity — it supports KMS-encrypted objects, all S3 regions, and all HTTP methods. OAI still appears in older material and in exam questions as the outdated option.
Bucket policy
One statement allowing s3:GetObject to the CloudFront service principal, conditioned on this distribution's ARN. Why: the condition is what stops any other distribution, in any AWS account, from using your bucket as its origin.
CloudFront distribution
Global edge network with a default CachingOptimized policy and HTTPS enforced. Why: it terminates TLS with its own certificate, so no domain or ACM setup is required, and it caches at roughly 600 locations.
Second cache behaviour
A /nocache/* path pattern using CachingDisabled. Why: path-pattern behaviours are the mechanism that routes /api/* to a different origin in a real architecture. Here it makes the caching difference measurable.
Lifecycle rules
Noncurrent versions expire after a day; objects under archive/ move to Standard-IA at 30 days and Glacier Instant Retrieval at 90. Why: versioning without expiry silently doubles storage, and tiering is the main S3 cost lever.
Custom error responses
403 and 404 both return /error.html. Why: S3 returns 403, not 404, for a missing key when the caller lacks ListBucket — so without this mapping a typo produces a confusing Access Denied.

Data flow
1
A viewer requests the distribution's domain over HTTPS. A plain HTTP request is redirected first, because the viewer protocol policy is redirect-to-https.
2
The nearest edge location checks its cache. On a hit the request never leaves the edge — no S3 request, no origin cost, single-digit millisecond latency.
3
On a miss, CloudFront makes an origin request and signs it with SigV4 using the Origin Access Control, presenting itself as the CloudFront service principal.
4
S3 evaluates the bucket policy. The statement allows s3:GetObject to that principal only when the source ARN matches this distribution, so the request is permitted.
5
The object is returned, cached at the edge according to the cache policy, and served. Subsequent viewers nearby are answered from the cache.
6
A request to the S3 URL directly carries no such signature and matches no statement, so it is denied — the public-access blocks and the policy agree.
7
Uploading a new version of an object does not update the edges. They keep serving the cached copy until its TTL expires or an invalidation is issued.
Key decisions
How should CloudFront be allowed to read the bucket?
Make the bucket public
Works instantly and is the single most common cause of accidental data exposure. It also means viewers can bypass CloudFront entirely, losing caching, logging and any protection in front of it.
Origin Access Identity
The legacy mechanism. Still functional, but it does not support KMS-encrypted objects or all regions, and AWS recommends against it for new work. It appears on the exam as the dated option.
Origin Access Control
Chosen. SigV4-signed origin requests, KMS support, every region, and a bucket policy condition that ties access to one specific distribution.
How should updated content reach viewers?
Wait for the TTL to expire
Free, and fine for content that changes rarely. With CachingOptimized the default TTL is 24 hours, which is far too slow for a deployment.
Invalidate /* after every deploy
Immediate, but only the first 1,000 paths per month are free and it is slow across all edges. Doing it on every deploy of a busy site becomes a real cost.
Versioned object names, invalidation as the exception
Chosen in principle: app.a1b2c3.js is a new object, so no invalidation is needed and caches never serve stale content. Reserve invalidation for the few files whose names cannot change, like index.html.
Why a missing file returns 403 S3 returns 403 Access Denied, not 404, for a key that does not exist when the caller has no s3:ListBucket permission — revealing whether an object exists would itself leak information. CloudFront's custom error response is what maps that back to a sensible 404 page. This trips people constantly when debugging a static site, and appears on the exam as a scenario where a correctly configured site returns Access Denied for one path.
Security · scaling · reliability · cost
Data protection
Four public-access blocks, encryption at rest, HTTPS enforced to viewers, and a bucket policy naming exactly one principal with one condition. Versioning means an overwrite or delete is recoverable rather than final.
Scaling
Nothing to configure. S3 scales to effectively unlimited storage and request rates; CloudFront absorbs traffic spikes at the edge and shields the origin. A viral page mostly never reaches S3 at all.
Failure modes
Both services are multi-AZ by design with no zone to lose. Realistic failures are operational: stale content because nobody invalidated, a 403 mistaken for a broken site, and lifecycle rules deleting data someone still wanted. Cache behaviour is the thing that surprises people, not availability.
Cost levers
Cache hit ratio is the main one — a hit costs edge transfer only, a miss adds an S3 request and origin transfer. Then storage class transitions, then expiring noncurrent versions. Price class can restrict the edge locations used if global reach is not needed.
Operational notes~15 min live
Deploy
3–5 minutes, nearly all of it the distribution propagating to edge locations. The bucket is created empty — the site returns an error until content is uploaded, which is the first step of the tour, not a fault.
Observe
Load the site, then request the S3 URL directly and get AccessDenied. Compare the x-cache response header between a first and second request to the same path.
Break
Upload a changed index.html and reload — the old content is still served, because the edge cached it. Then invalidate and watch it update. Also request a path that does not exist and see the 403-to-404 mapping.
Destroy
Around 4 minutes. A distribution must be disabled before it can be deleted, which CloudFormation handles, and the bucket must be emptied first — including every old version, which is what versioning adds to teardown.
Watch these three things
  1. The x-cache header: Miss from cloudfront then Hit from cloudfront. That single header explains most CDN behaviour.
  2. The direct S3 request failing. The site works and the bucket is genuinely private — those are not in tension.
  3. How long stale content survives after an upload. That interval is the TTL, and it is why deployments use versioned filenames.
Red flag — don't Never "fix" a CloudFront 403 by making the bucket public. The 403 almost always means the OAC or bucket policy is wrong, or the key does not exist — and turning off public access blocks exposes every object in the bucket to the entire internet, permanently and silently, while appearing to solve the problem. Check the policy's source-ARN condition first.

Deliberately absent. No custom domain or ACM certificate — worth knowing that a CloudFront certificate must live in us-east-1 regardless of where anything else is. No signed URLs or cookies, which is how you restrict access to paying users. No Lambda@Edge or CloudFront Functions, which run code at the edge for header manipulation and request rewriting. And no WAF, which attaches to a distribution to filter requests before they reach any origin.

Storage classes, in one line each Standard for active data. Standard-IA for infrequent access with millisecond retrieval, cheaper storage but a per-GB retrieval fee and a 30-day minimum. One Zone-IA is the same but in a single AZ — cheaper, and it is gone if that zone is lost. Glacier Instant Retrieval for archives still needing millisecond access; Flexible Retrieval for minutes to hours; Deep Archive for twelve hours and the lowest price. Intelligent Tiering moves objects automatically for a small monitoring fee, and is the right answer whenever the access pattern is described as unknown or changing.
