Lab 04 put a DynamoDB table behind an API and moved on. This lab stays with the table: how a single-table design carries two unrelated item types without them colliding, how a GSI and an LSI answer two access patterns the primary key can't, what a condition expression actually buys you, and how Streams turns "an item changed" into "something happened" without anyone polling.

Scope In scope: composite keys, sparse global and local secondary indexes, on-demand billing, conditional writes, TransactWriteItems, TTL, point-in-time recovery, and DynamoDB Streams as a Lambda event source. Out of scope: DAX, global tables, and provisioned capacity with auto scaling — all three are covered in the exam notes, none of them are cheap enough to justify deploying for a lab that tears itself down in minutes.

Reference architecture

01. One table, two access patterns, one event stream
In one line

Everything in this lab is one DynamoDB table doing three jobs at once — primary-key lookups, index-backed queries, and a change feed — which is closer to how DynamoDB gets used in production than a table-per-entity design ever is.

Context & requirements

What it must do

  • Store orders and products in one table
  • Answer "every order in status X" without a Scan
  • Answer "one customer's orders by size" without a Scan
  • Turn a status change into an audit record automatically

How it must behave

  • Stock can never go negative under concurrent writers
  • An order and its stock deduction move together, or not at all
  • Abandoned orders expire on their own, for free
  • The stream consumer holds exactly two permissions, on two different ARNs

Constraints

  • No VPC, no API layer — driven straight against the AWS APIs
  • On-demand billing throughout
  • The LSI must exist at table-creation time — no retrofitting it
  • Idle cost must round to zero
High-level design
DynamoDB table
Composite key pk + sk, on-demand billing, holding orders, products and audit records in one table. Why: one table means one thing to back up, one stream to consume, and no cross-table transaction needed for data that's naturally related.
gsi1-status-by-time
Global secondary index, partition key status, sort key createdAt. Why: "every PENDING order" cuts across every customer's partition — only a GSI with its own partition key can answer that without a Scan. Sparse by construction: products never carry a status, so they never appear here.
lsi1-by-total
Local secondary index, same partition key as the base table (pk), sort key total. Why: "this customer's orders, biggest first" needs the same partition as the base table but a different order — the one job an LSI does that a GSI can't do more cheaply.
Stream processor (Lambda)
Python 3.12, triggered by an event source mapping on the table's stream. Why: reacts to NEW_AND_OLD_IMAGES to detect a status transition and write an audit item back — the only way to get "notify something when a record changes" without the writer knowing anyone is listening.
Stream role
Two statements: stream-read actions scoped to <table-arn>/stream/*, and PutItem scoped to the table ARN itself. Why: these are genuinely different permissions on different resources — removing one silences the function, removing the other makes it fail loudly. The failure injection is built around that split.

Data flow
1
A caller writes a product with stock and version attributes and no status or total — those only exist on order items, which is why this item will never appear in either index.
2
A stock decrement carries ConditionExpression: stock > :zero. DynamoDB evaluates the condition and applies the write as one atomic operation; if the condition is false, the item is left exactly as it was and the call returns ConditionalCheckFailedException.
3
TransactWriteItems decrements stock and creates the order in a single all-or-nothing call — there is no window in which the order exists without the matching stock deduction, unlike two separate calls or BatchWriteItem.
4
The order item carries status and createdAt, so it's automatically projected into gsi1-status-by-time, and it carries total under the same pk as the base table, so it's projected into lsi1-by-total too — no second write, no second table.
5
A later UpdateItem flips the order's status. The table's stream, set to NEW_AND_OLD_IMAGES, carries both the before and after value of every attribute to the event source mapping.
6
The stream processor compares old and new status. When they differ, it writes one audit item back to the same table with pk = AUDIT — a single partition a later Query can read in order, exactly like Lab 04's notes pattern.
7
If expiresAt passes, the background TTL sweep deletes the item for free and the deletion itself appears on the stream as a REMOVE event carrying a system principal — the processor tells this apart from a manual delete and logs it accordingly.
8
Everything the function prints lands in CloudWatch Logs asynchronously. During the failure injection, this is where an AccessDeniedException for the write-back PutItem appears — while the stream read that triggered the invocation keeps succeeding.
Key decisions
How should "every order in this status" be answered?
Scan with a filter expression
Reads every item in the table — orders, products, and every audit record — then discards whatever doesn't match. Cost and latency grow with total table size forever, regardless of how few PENDING orders actually exist.
Query gsi1-status-by-time
Chosen. A GSI can have a partition key the base table doesn't have at all. Because the index is sparse — only items with a status attribute appear in it — the index stays small even as the audit trail grows unbounded in the base table.
How should "this customer's orders, biggest first" be answered?
Add a second GSI keyed on pk + total
Works, but costs its own write capacity and storage for an index whose partition key is identical to the base table's — paying for a feature (a different partition key) this access pattern never needed.
Query lsi1-by-total
Chosen. An LSI shares the base table's partition key by definition, which is exactly this access pattern's shape. The trade is that it must be declared at table creation — there is no adding one to a live table, capped at five per table either way.
How should the order write and the stock deduction move together?
BatchWriteItem
Despite the name, each item in the batch is written independently — a partial failure can leave the order created with no matching stock deduction, or vice versa. It's a batching optimisation, not a consistency guarantee.
TransactWriteItems
Chosen. Every action in the transaction succeeds together or none of them apply, at roughly double the write-capacity cost of doing the same writes individually — the price of the atomicity guarantee.
The detail that decides GSI vs. LSI on the exam A global secondary index can be added, changed or removed on a table that's already live, and its partition key can be anything. A local secondary index must be declared when the table is created, is capped at five, and its partition key is always the base table's. When a question says "the table already exists in production and needs a new access pattern," the answer is a GSI — an LSI is no longer on the table.
Security · scaling · reliability · cost
Data protection
The stream processor holds two narrow statements rather than dynamodb:*: stream-read actions on the stream ARN, PutItem on the table ARN. Point-in-time recovery is enabled from the template, giving continuous restore to any second in the last 35 days without a scheduled backup job.
Scaling
On-demand billing means no capacity to plan for on the table or either index. The real scaling risk here is a hot partition — one heavily written partition key throttles independently of the table's overall headroom, which no amount of raised capacity fixes on its own; the fix is key design.
Failure modes
A denied stream-read permission stops invocations entirely with no error anywhere — the function simply never runs. A denied write-back permission lets the function run and fail loudly with a logged AccessDeniedException. Blast radius is one function; the table itself is untouched either way.
Cost levers
Idle is free. Under load, the levers are avoiding Scan, choosing conditional writes over read-then-write round trips, and reserving TransactWriteItems for writes that genuinely need atomicity — its roughly 2× capacity cost is wasted on writes that don't.
Operational notes~20 min live
Deploy
Under a minute. A table with two indexes, a role, a log group and a function — nothing here has RDS's multi-minute provisioning or a NAT gateway's dependency chain.
Observe
Force a ConditionalCheckFailedException on purpose, then run a TransactWriteItems call and confirm both writes landed together. Watch the audit item appear in CloudWatch Logs within seconds of a status change, with no polling anywhere.
Break
Remove dynamodb:PutItem from the stream role. Reads off the stream keep happening — the function keeps getting invoked — but the write-back fails loudly. Removing a stream-read action instead would have failed silently: same role, opposite symptom.
Destroy
Under a minute. Point-in-time recovery stops billing the moment the table is gone — there is no separate backup vault left holding a charge.
Watch these three things
  1. Which items show up in gsi1-status-by-time versus lsi1-by-total — neither index contains every item in the table, and that's by design, not a bug.
  2. The exact wording of ConditionalCheckFailedException — it's the normal, expected outcome of a condition expression doing its job, not a system error.
  3. How a TTL-driven REMOVE looks identical to a manual delete on the outside, distinguishable only by the principal recorded in the stream record.
Red flag — don't Never reach for BatchWriteItem when two writes must succeed or fail together — it looks like a transaction and isn't one. The same trap catches an LSI added "later" to save a design decision for after launch: by the time the access pattern is needed, the table already exists, and an LSI can no longer be added to it at all.

For comparison, adding DAX in front of this table for microsecond reads would introduce the first genuinely hourly charge in the lab — a minimum three-node cluster running continuously, which is exactly why it isn't deployed here even though it's real exam content. Global tables would add per-region replicated write costs for the same reason.

Deliberately absent. DAX (in-memory caching in front of the table — covered in the exam notes, not deployed). Global tables (multi-region active-active replication — same). Provisioned capacity with auto scaling — on-demand suits a lab with no steady traffic to forecast against. An API layer of any kind: this lab is about what the database does, not what fronts it.

The exam's framing DynamoDB questions almost always hinge on one access pattern described in prose. Translate it first: does it need the base table's key, a different partition key entirely (GSI), the same partition with a different sort (LSI), atomicity across items (TransactWriteItems), or a reaction to change (Streams)? Naming the right primitive is the whole question — the API call names follow automatically once the primitive is right.
