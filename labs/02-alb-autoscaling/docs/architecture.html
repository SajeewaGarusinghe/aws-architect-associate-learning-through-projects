Lab 01 built the network. This lab puts a real workload inside it and makes the second availability zone earn its place. The private subnet in AZ b, left deliberately empty last time, now runs half the fleet.

Scope In scope: how an Application Load Balancer spans availability zones, target groups and health checks, Auto Scaling group sizing and instance replacement, the difference between EC2 and ELB health check types, and security groups that reference other security groups. Out of scope: HTTPS and certificates, scaling policies driven by metrics, and any database — the tier here is deliberately stateless.

Reference architecture

01. One entry point, two zones, no way out
In one line

The load balancer is the only component in this architecture with a public address; the instances behind it have no public IP, no NAT gateway and no default route, so the only traffic they can ever see is traffic the load balancer forwards to them.

Context & requirements

What it must do

  • Serve HTTP from more than one availability zone
  • Replace an instance automatically when it fails
  • Survive the loss of an entire availability zone
  • Show which instance answered each request

How it must behave

  • Instances unreachable except through the load balancer
  • No public IP on any instance
  • A failed web server is replaced, not just a failed host
  • IMDSv2 required on every instance

Constraints

  • No NAT gateway — the tier must need no egress
  • CIDR 10.30.0.0/16, distinct from Labs 00 and 01
  • Under $0.06/hour while live
  • Destroyed by a single delete-stack
High-level design
Internet Gateway
Attached to the VPC, with a 0.0.0.0/0 route in the public route table only. Why: the load balancer's nodes live in the public subnets and need it; nothing else in this stack does.
Public subnets ×2
10.30.1.0/24 and 10.30.2.0/24, one per AZ. Why: an ALB requires subnets in at least two availability zones — that requirement is what makes it inherently multi-AZ, and it is why these two subnets exist at all.
Application Load Balancer
Internet-facing, one logical resource with a node in each public subnet, resolved by a single DNS name. Why: it terminates every client connection, so the fleet behind it can change size and membership without any client noticing.
Target group
HTTP :80, health check / every 15 seconds, healthy after 2 passes, unhealthy after 2 failures, deregistration delay shortened to 30 seconds. Why: the target group — not the load balancer — owns the health check, and it is the object that decides which instances receive traffic.
Auto Scaling group
Minimum 2, desired 2, maximum 4, spread across both private subnets, with health check type ELB. Why: it keeps the fleet at the desired size and distributes instances evenly across AZs automatically — no manual placement decisions.
EC2 t3.micro ×2
Amazon Linux 2023 in the private subnets, IMDSv2 required, serving a page naming their own instance ID and availability zone. Why: the page makes load balancing visible — reload it and watch the zone change.
Launch template
The versioned blueprint the Auto Scaling group uses: AMI, instance type, security group, metadata options, user data. Why: launch templates support versioning and every current EC2 feature; launch configurations, their predecessor, are deprecated and cannot be modified.
ALB security group
Inbound TCP 80 from 0.0.0.0/0. Why: this is the only place in the stack where the internet is allowed in, which makes the attack surface a single reviewable object.
App security group
Inbound TCP 80 whose source is the ALB's security group, not a CIDR range. Why: the rule keeps working as instances are replaced and subnets change, and it cannot accidentally admit anything else in the VPC. This construct appears constantly on the exam.
Private route table
Carries the local route and nothing else — no 0.0.0.0/0 entry at all. Why: with no NAT gateway and no default route, the web tier has literally no internet path. It saves $0.059/hour and removes a whole category of risk.

Data flow
1
A browser resolves the load balancer's DNS name. It returns the public addresses of the ALB nodes — more than one, one per availability zone — so DNS itself is the first layer of distribution.
2
The client opens a TCP connection to one node. The ALB security group admits it on port 80; it is the only inbound rule in the stack that mentions the internet.
3
The ALB terminates that connection and opens its own, separate connection to a healthy target chosen by round robin. The client and the instance never speak directly.
4
The app security group evaluates the new connection. Its rule names the ALB's security group as the source, so the packet is admitted regardless of which node or private address it came from.
5
The instance answers from a page written at boot from its own metadata. The reply returns through the ALB; the security group is stateful, so no outbound rule is needed.
6
Continuously and independently: the target group requests / from every registered target every 15 seconds. Two consecutive failures mark a target unhealthy and it stops receiving traffic.
7
Because the Auto Scaling group's health check type is ELB, that unhealthy verdict also causes the group to terminate the instance and launch a replacement in the same availability zone.
Key decisions
What should the Auto Scaling group treat as "unhealthy"?
Health check type EC2
The default. It watches only the hypervisor-level status checks, so it replaces an instance that has crashed or lost networking — but not one whose operating system is fine while the web server has died. The load balancer stops sending traffic there, and the group never notices.
Health check type ELB
Chosen. The group inherits the target group's verdict, so a failed application is replaced, not just a failed host. Requires a grace period — here 120 seconds — or instances get killed before their web server has finished starting.
How should the web tier restrict inbound traffic?
Allow the VPC CIDR 10.30.0.0/16
Simple, and wrong. Every resource in the VPC — now or in future — can reach the web tier on port 80, including anything an attacker manages to land elsewhere in the network.
Allow the public subnet CIDRs
Narrower, but still admits anything that ever lands in those subnets, and breaks if the subnets are renumbered or a third AZ is added.
Source = the ALB's security group
Chosen. The permission follows the load balancer itself rather than any address range, so it survives instance replacement, subnet changes and new AZs, and admits nothing else by construction.
Two objects, two different jobs The target group decides which instances receive traffic. The Auto Scaling group decides which instances exist. They are separate systems, and they only agree because health check type is set to ELB. Leave it at the default EC2 and you get the classic failure: a broken instance that the load balancer has correctly stopped using, sitting there indefinitely, never replaced, quietly reducing your capacity.
Security · scaling · reliability · cost
Data protection
Exactly one inbound rule in the stack mentions the internet, and it is on the load balancer. The instances have no public address and no route to one. IMDSv2 is required, which blocks the SSRF-style metadata theft that IMDSv1 allowed. Traffic is plain HTTP — acceptable only because this is a lab; production would terminate TLS at the ALB with an ACM certificate.
Scaling
Manual between 2 and 4 instances here. The Auto Scaling group balances across AZs on its own. In production this is where a target tracking policy goes — "keep average CPU at 50%" — which is almost always the right exam answer over step or simple scaling.
Failure modes
Losing one instance: the group replaces it in about two minutes, and the ALB drains it in 30 seconds meanwhile. Losing a whole AZ: the ALB stops resolving to that zone's node and the group rebalances into the survivor. Blast radius is one AZ — genuinely better than Lab 01, where a single NAT gateway made AZ a critical for everything.
Cost levers
Removing the NAT gateway saves $0.059/hour — more than the load balancer itself costs. It was possible only because this workload genuinely needs no egress; a tier that must fetch packages or call third-party APIs cannot make the same trade. The ALB bills hourly plus capacity units, and like the NAT gateway it charges whether or not anyone visits.
Operational notes~20 min live
Deploy
Four to five minutes. The ALB takes the longest to provision. Targets stay initial for up to a minute after the instances are running — the health check needs two consecutive passes before traffic flows, so expect a 503 if you load the page too early.
Observe
Load the site and reload repeatedly. The availability zone on the page changes as the ALB round-robins. Watch the same two instances appear in the target group as healthy.
Break
Terminate one instance and watch three systems react in order: the target group marks it unhealthy, then draining; the Auto Scaling group launches a replacement in the same AZ; the new instance passes two health checks and starts serving. Then point the health check at a path that does not exist and watch every target fail at once — the site returns 503 while the instances themselves are perfectly fine.
Destroy
One delete-stack. The Auto Scaling group must terminate its instances before the subnets can be deleted, so this takes longer than Lab 01 — around four minutes.
Watch these three things
  1. The target group's Targets tab during the failure injection — it is the only place where initial, healthy, unhealthy and draining are all visible as they happen.
  2. The Auto Scaling group's Activity tab, which narrates its own decisions in plain English, including why it terminated something.
  3. Which AZ the replacement instance lands in. The group rebalances to keep the zones even — it does not simply launch wherever is convenient.
Red flag — don't Never set the Auto Scaling health check grace period shorter than the time an instance needs to boot and start serving. Too short and the group kills each new instance before it can pass its first health check, then launches another, and another — an infinite replacement loop that bills for every one of them. If an ASG is "constantly cycling instances", the grace period is the first thing to check.

Deliberately absent. No HTTPS listener or ACM certificate — worth knowing that ACM certificates are free and that TLS terminates at the load balancer, but neither needs to be deployed to be understood. No metric-driven scaling policy, because watching CPU climb takes longer than this lab's entire budget. No database: the tier is stateless on purpose, so that any instance can answer any request, which is exactly the property that makes horizontal scaling work. Lab 03 adds the database and the state problem that comes with it.

A note on the teardown An Auto Scaling group will faithfully replace instances you terminate by hand — that is its entire purpose. Deleting the stack is therefore the only correct way to stop this lab; terminating the instances individually just triggers replacements and leaves the load balancer billing. If a teardown ever appears stuck, it is almost always waiting for the group to drain, which it will do on its own.
