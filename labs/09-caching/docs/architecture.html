Lab 04 deliberately kept its function out of a VPC and said so. This lab puts one inside a VPC, because it has the only good reason to: ElastiCache is reachable from nowhere else. That decision brings back subnets, security groups and a route table — and the cost of forgetting a VPC endpoint.

Scope In scope: the cache-aside pattern, TTL as a staleness bound, Lambda inside a VPC and what that changes, gateway endpoints instead of NAT, and where caching belongs relative to the database. Out of scope: write-through and write-behind caching, Redis cluster mode and replication, and DynamoDB DAX.

Reference architecture

01. Ask the cache first, the database second
In one line

Cache-aside puts the application in charge: it checks the cache, and only on a miss does it read the system of record and populate the cache — which means the cache can be emptied, resized or lost entirely without any data being lost, only latency.

Context & requirements

What it must do

  • Serve repeated reads without touching the database
  • Populate the cache on a miss, automatically
  • Bound how stale an answer can be
  • Keep working when the cache is unavailable

How it must behave

  • Redis reachable only from the function's security group
  • No internet route anywhere in the VPC
  • Hit and miss distinguishable in the response
  • Cache loss must cost latency, never data

Constraints

  • cache.t3.micro, single node
  • No NAT gateway — a gateway endpoint instead
  • CIDR 10.50.0.0/16
  • Under $0.04/hour
High-level design
HTTP API
The same public entry point as Lab 04. Why: API Gateway is outside the VPC entirely — it invokes the function through the Lambda service, so no network path between them is required or possible.
Lambda in a VPC
Attached to both private subnets, 512 MB. Why: a VPC-attached function runs behind elastic network interfaces in your subnets, which is the only way to reach ElastiCache. It also means the function inherits your routing — including the absence of a route to the internet.
ElastiCache for Redis
A single cache.t3.micro node, no replica. Why: the cache is deliberately disposable. Losing it costs latency and a burst of database reads, never data — which is precisely what cache-aside buys you.
DynamoDB table
The system of record, on-demand billing. Why: the cache is an optimisation in front of it, never a replacement. Every value in Redis originated here and can be rebuilt from here.
DynamoDB gateway endpoint
A prefix-list route in the private route table. Why: without it the VPC-attached function could not reach DynamoDB at all. The alternative is a NAT gateway at $0.059/hour; the endpoint is free, and this is the single most valuable cost lesson in the lab.
Security group chain
Redis admits port 6379 only from the function's security group. Why: the third appearance of this construct in the curriculum — the permission follows the function, not any address range.
60-second TTL
Set with SETEX when a value is cached. Why: the TTL is the contract about staleness. It is the maximum time a reader can see a value that no longer matches the database, and choosing it is a business decision, not a technical one.

Data flow
1
A request arrives at the HTTP API, which invokes the function through the Lambda service. No network path exists between them — API Gateway is not in the VPC.
2
The function runs behind an elastic network interface in a private subnet and issues GET product:p-1 to Redis over the VPC's private address space.
3
On a hit the value is returned immediately. The request never reaches DynamoDB and never leaves the subnet — typically a few milliseconds.
4
On a miss the function reads DynamoDB. That traffic matches the prefix-list route and leaves through the gateway endpoint, which costs nothing; with no endpoint and no NAT it would simply time out.
5
The value is written back with SETEX and a 60-second TTL, so the next reader hits the cache and the entry cannot outlive its staleness budget.
6
The response reports CACHE HIT or CACHE MISS and elapsed milliseconds, making the difference visible rather than asserted.
7
If Redis is unreachable the function logs it and reads DynamoDB anyway. The cache is an optimisation; its failure is a slowdown, not an outage.
Key decisions
How should the VPC-attached function reach DynamoDB?
A NAT gateway
Works, and it is what most people reach for. It costs $0.059/hour plus data processing — more than double this entire lab — to send AWS-service traffic out to the internet and back into AWS.
Interface endpoints for DynamoDB
DynamoDB does support them, but they bill hourly per AZ. Right when traffic must arrive from on-premises over Direct Connect; wasteful here.
A gateway endpoint
Chosen. Free, a route-table entry rather than an ENI, and available for exactly two services: S3 and DynamoDB. If a question has a VPC resource talking to either one, this is almost always the intended answer.
Where should the cache sit?
In front of everything, at the edge
CloudFront caches responses close to users and is excellent for static content — but it cannot cache a per-user query result that depends on database state.
Inside the function's memory
Free and fast, but each execution environment has its own copy. Nothing is shared, nothing is invalidated, and a scaled-out function has dozens of inconsistent caches.
A shared cache beside the application
Chosen. Every function instance sees the same entries, one write-back benefits all subsequent readers, and TTL behaviour is consistent across the fleet.
Redis or Memcached — the exam's framing Memcached is simple, multi-threaded, and purely a cache: no persistence, no replication, no failover. Redis adds replication, Multi-AZ with automatic failover, snapshots, transactions, and data structures like sorted sets — which is why it is the answer whenever a question mentions leaderboards, pub/sub, persistence, or high availability. Memcached is the answer when the question emphasises simplicity or the ability to scale horizontally by adding nodes.
Security · scaling · reliability · cost
Data protection
Redis is reachable only from the function's security group, in subnets with no internet route, and holds only copies of data that lives durably in DynamoDB. The execution role grants two DynamoDB actions on one table.
Scaling
A VPC-attached function scales like any other, but each concurrent execution needs an ENI — so subnet address space becomes a concurrency limit, which is a genuine production surprise. Redis scales by node size, or by replicas for reads, or by cluster mode for sharded writes.
Failure modes
A single cache node has no failover: losing it means every request misses until it returns, which is a thundering herd against the database. Production would use Multi-AZ with automatic failover. The subtler failure is a TTL longer than the business tolerates, serving confidently wrong data.
Cost levers
The node is the only hourly charge here, and unlike Lambda it bills whether or not anything uses it — a cache is a server, with all that implies. Not provisioning a NAT gateway saves twice the node's cost. Hit ratio is the lever that decides how much DynamoDB capacity you avoid.
Operational notes~20 min live
Deploy
6–9 minutes, nearly all of it the ElastiCache node. Everything else is created in under a minute while Redis provisions.
Observe
Call the endpoint twice. The first reports CACHE MISS with a larger elapsed time; the second reports CACHE HIT, faster. Wait 60 seconds and the miss returns as the TTL expires.
Break
Remove the Redis ingress rule from the cache security group. Every request becomes a miss and the logs show cache unavailable — the API keeps working, only slower, which is the resilience property of cache-aside. Restore the rule.
Destroy
8–12 minutes. The cache node must be deleted, and Lambda's ENIs can take several minutes to detach before the subnets and security groups can go. A teardown that appears stuck on the security group is almost always waiting for an ENI.
Watch these three things
  1. The ms figure between a hit and a miss. The gap is what the cache is actually buying, in the only units that matter.
  2. The TTL expiring. Sixty seconds after the first call the miss returns — the entry was not evicted for space, it aged out by design.
  3. The API still answering with Redis blocked. A cache whose failure takes the service down is not a cache, it is a dependency.
Red flag — don't Never put a Lambda function in a VPC unless it must reach something that only exists there. A VPC-attached function inherits your routing, so it loses internet access entirely unless you add a NAT gateway, and it consumes ENIs and subnet addresses as it scales. "For security" is not a reason — S3, DynamoDB, SQS and most AWS services are not in your VPC, and a function calling them is no safer inside one.

The gateway endpoint is worth restating: adding a NAT gateway instead would have made this lab more than three times the price, to do the same work more slowly.

Deliberately absent. No Redis replica or Multi-AZ failover — correct for production, and it would double the only hourly cost here. No write-through caching, where the application writes to cache and database together: it keeps the cache warmer at the price of writing data nobody reads. No DAX, which is a DynamoDB-specific cache requiring no application change at all, and the right answer when a question asks for microsecond DynamoDB reads without rewriting the code.

Choosing a caching layer CloudFront caches responses at the edge, close to users — static content and whole HTTP responses. ElastiCache caches arbitrary application data beside the application — query results, sessions, computed values. DAX caches DynamoDB specifically, transparently, in microseconds. API Gateway caching caches whole API responses per stage, billed hourly. Read the question for what is being cached and where the latency is, and the choice is usually unambiguous.
