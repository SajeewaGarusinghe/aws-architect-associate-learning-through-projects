Scope In scope: VPC address planning, subnet placement, routing, the two egress paths (NAT gateway and VPC endpoints), stateful versus stateless traffic filtering, and flow-log observability. Out of scope: load balancing, auto scaling, and databases — those arrive in Labs 02 and 03 and are built on top of exactly this network.

Reference architecture

01. The network and its two exits
In one line

A subnet is not "public" or "private" because of anything on the subnet — it is public only because the route table attached to it sends 0.0.0.0/0 to an internet gateway. Everything else in this lab follows from that single fact.

Context & requirements

What it must do

  • Isolate workloads in subnets with no inbound internet path
  • Still let those workloads fetch patches and talk to AWS APIs
  • Provide an interactive shell without opening SSH
  • Record every accepted and rejected packet

How it must behave

  • No inbound security-group rule anywhere in the stack
  • No SSH key, no bastion host, no public IP on the instance
  • Management plane survives loss of the internet route
  • Destroyed by a single delete-stack

Constraints

  • CIDR must not overlap 10.0.0.0/16, already in use
  • Region ap-southeast-2, account past free tier
  • Total spend under $0.10 for the session
  • Account quota: 5 VPCs, 5 Elastic IPs
High-level design
VPC 10.20.0.0/16
An isolated virtual network with 65,536 addresses, carved into four /24 subnets. Why: the range deliberately avoids 10.0.0.0/16, which the session host already occupies — two VPCs with overlapping CIDRs can never be peered, and that mistake is permanent without a rebuild.
Public subnets ×2
10.20.1.0/24 in AZ a and 10.20.2.0/24 in AZ b. Why: they hold only infrastructure that must be internet-facing. In this lab that is the NAT gateway alone; in Lab 02 it becomes the load balancer.
Private subnets ×2
10.20.11.0/24 and 10.20.12.0/24. Why: workloads belong here. The .11/.12 numbering leaves .3–.10 free, so later tiers slot in without renumbering.
Internet Gateway
A horizontally scaled, highly available VPC attachment. Why: it is the only component that performs one-to-one NAT between a private address and a public IPv4 address. It costs nothing and cannot be a bottleneck.
NAT Gateway + Elastic IP
Managed source NAT for outbound-only traffic, placed in public subnet a. Why: private instances need to reach the internet, but nothing on the internet may initiate a connection to them. This is the single most expensive component in the stack.
Route tables ×2
rt-public sends 0.0.0.0/0 to the internet gateway; rt-private sends it to the NAT gateway and additionally carries a prefix-list route for S3. Why: these two rows are the entire difference between a public and a private subnet.
VPC interface endpoints ×3
ssm, ssmmessages and ec2messages, each an elastic network interface inside private subnet a with private DNS enabled. Why: they give Session Manager a path that never touches the internet, which is what lets the shell survive the failure injection below.
S3 gateway endpoint
Not a network interface at all — a prefix-list route injected into rt-private. Why: gateway endpoints are free where interface endpoints bill hourly, so S3 and DynamoDB traffic should never be paying NAT data-processing charges.
EC2 t3.micro + IAM role
Amazon Linux 2023 in private subnet a, no public IP, no key pair, carrying AmazonSSMManagedInstanceCore. Why: the SSM agent authenticates with the instance role and dials outward, so an inbound rule is never required.
Security group
Zero inbound rules; egress limited to TCP 443 and 80. Why: security groups are stateful — the reply to an allowed outbound request is admitted automatically, with no matching inbound rule.
Network ACL
A custom ACL on both private subnets: rule 110 allows the VPC range, 120 allows inbound TCP 1024–65535, and outbound allows everything. Why: NACLs are stateless, so rule 120 exists purely to re-admit return traffic. Deleting it breaks outbound connections even though the security group is untouched.
VPC Flow Logs
All traffic, VPC-wide, delivered to a CloudWatch log group with one-day retention. Why: the ACCEPT/REJECT field is the only direct evidence of which control actually dropped a packet.

Data flow
1
The instance runs curl https://example.com. Its security group permits TCP 443 outbound, so the packet leaves the elastic network interface.
2
The custom network ACL evaluates the packet on the way out against its outbound rules, which allow everything. The ACL is stateless, so it will evaluate the reply separately on the way back in.
3
rt-private matches 0.0.0.0/0 and forwards to the NAT gateway in public subnet a — a cross-subnet, same-AZ hop.
4
The NAT gateway rewrites the source address to its Elastic IP and records the translation. rt-public matches 0.0.0.0/0 and forwards to the internet gateway.
5
The reply returns to the Elastic IP. The NAT gateway reverses the translation; ACL rule 120 admits it on an ephemeral port; the security group admits it automatically because it is stateful.
6
Separately and continuously: the SSM agent holds an outbound connection to the three interface endpoints, resolved by private DNS to addresses inside 10.20.11.0/24. This traffic never reaches the route table's default route, so it is unaffected by anything that happens to the NAT gateway.
7
Traffic to S3 matches the prefix-list route rather than 0.0.0.0/0, leaving through the gateway endpoint at no charge.
8
Every packet in steps 1–7 is recorded to CloudWatch Logs with an ACCEPT or REJECT verdict, asynchronously and with a few minutes' delay.
Key decisions
How should the private instance reach the AWS control plane?
A bastion host in a public subnet
Requires an inbound SSH rule, a key pair to distribute and rotate, and a second instance to patch. It is an internet-facing attack surface that exists only to reach machines that are not.
Session Manager over the NAT gateway
Works, and costs nothing extra — but management traffic then depends on the same path as workload traffic. Lose the NAT gateway and you lose the shell you need to diagnose it.
Session Manager over interface endpoints
Chosen. Costs $0.039/hr for three endpoints, and buys an administrative path that is independent of the internet route. The failure injection demonstrates exactly this.
How many NAT gateways?
One per availability zone
The production answer. Each AZ's private subnets egress through their own NAT, so an AZ failure is contained and no cross-AZ data charges accrue. It doubles the hourly cost.
One, in AZ a
Chosen for this lab. Halves the cost and makes the trade-off visible: AZ a is now a single point of failure for both private subnets, and any egress from AZ b pays a cross-AZ transfer charge.
The distinction the exam keeps testing A security group is stateful: allow a request out and the reply is admitted automatically. A network ACL is stateless: it evaluates every packet in each direction independently, so the reply needs its own inbound rule on the ephemeral port range 1024–65535. That is the only reason ACL rule 120 exists. If a question describes outbound connections that hang or time out while the security group is clearly correct, the missing ephemeral-port ACL rule is almost always the answer.
Security · scaling · reliability · cost
Data protection
No inbound rule exists anywhere in the stack and the instance has no public address, so it is unreachable from the internet by construction rather than by policy. Access is authenticated through IAM and logged to CloudTrail, not through a shared key.
Scaling
The internet gateway and NAT gateway scale automatically — NAT to 100 Gbps. The real constraint is address space: a /24 yields 251 usable addresses, because AWS reserves five in every subnet.
Failure modes
Losing AZ a removes outbound internet for both private subnets, and removes the interface endpoints too, since all three live in one subnet. Blast radius is the whole stack — an accepted consequence of optimising a teaching lab for cost.
Cost levers
The NAT gateway is 51% of the hourly cost and bills for data processed on top. Routing S3 and DynamoDB through free gateway endpoints is the first optimisation; replacing NAT with interface endpoints for specific services is the second; deleting the stack is the third and the one this lab actually uses.
Operational notes~20 min live
Deploy
Roughly three minutes, nearly all of it the NAT gateway and the three interface endpoints. The EC2 instance reaches running well before Session Manager will accept a connection — the agent needs the endpoints to exist first.
Observe
Work through the console tour against this diagram. The VPC resource map is the fastest way to confirm subnet-to-route-table associations are what the template intended.
Break
Delete the 0.0.0.0/0 route from rt-private. Outbound internet from the instance stops immediately; the Session Manager shell stays connected, because that traffic never used the route. Restore the route and internet returns without touching the instance.
Destroy
One delete-stack, then a tag sweep to prove the NAT gateway and Elastic IP are actually gone rather than merely detached.
Watch these three things
  1. The route tables — which subnet is associated with which, and what the single 0.0.0.0/0 row points at in each.
  2. The NAT gateway's Elastic IP, then the source address the instance reports from curl ifconfig.me. They are the same address, and that is the whole point of NAT.
  3. The flow logs after the failure injection — the REJECT records name the traffic that the missing route stranded.
Red flag — don't Never leave a NAT gateway running after a lab. It bills $0.059 every hour whether or not a single packet crosses it, which is about $43 a month for an idle resource, and it is the most common way a personal AWS account quietly accumulates a bill. The Elastic IP keeps charging too. This is precisely why teardown is verified by tag sweep rather than trusted to DELETE_COMPLETE.

Deliberately absent. There is no load balancer, no auto scaling group, no database, and no second NAT gateway. Each is a cost this lab does not need to make its point, and each arrives in a later lab where it is the subject rather than scenery. The private subnet in AZ b is left empty on purpose — Lab 02 fills it, and the contrast between a single-AZ and a genuinely multi-AZ deployment is easier to feel when you have built both.

Verification, not assumption CloudFormation reporting DELETE_COMPLETE means the stack record is gone. It is not independent evidence that no billable resource survived — a NAT gateway can sit in deleting for minutes, and a released Elastic IP that was never associated still appears in the account. Teardown therefore re-queries EC2 by tag and fails loudly if anything answers.
