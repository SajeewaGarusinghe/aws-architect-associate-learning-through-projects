Every previous lab connected components synchronously: a request arrives, something answers it, and if the thing on the other end is down the caller finds out immediately. This lab removes that coupling. The publisher does not know who is listening, does not wait for them, and is unaffected when one of them breaks.

Scope In scope: SNS fan-out, SQS as a buffer, message filtering at the topic, visibility timeout, dead-letter queues and redrive, and what "at least once delivery" obliges you to build. Out of scope: FIFO queues, EventBridge, and Step Functions — all worth knowing, none needed to see the pattern work.

Reference architecture

01. Publish once, consume independently
In one line

A queue between two components converts a failure into a delay: the producer keeps working at its own pace, the consumer retries on its own schedule, and the only thing that changes when the consumer dies is how long messages sit waiting.

Context & requirements

What it must do

  • Deliver every order to several consumers
  • Survive a consumer being offline
  • Retry transient failures automatically
  • Quarantine messages that can never succeed

How it must behave

  • The publisher never learns who subscribes
  • A failing consumer must not block the queue
  • Failures bounded to three attempts
  • Evidence of failures kept for 14 days

Constraints

  • No EC2 and no VPC
  • Idle cost exactly zero
  • Consumer timeout below the visibility timeout
  • Destroyed by a single delete-stack
High-level design
SNS topic
A push-based fan-out point. Why: one publish reaches every subscriber. Adding a fifth consumer later means adding a subscription — the publisher is never modified, which is the whole point of decoupling.
Orders queue
SQS standard, 60-second visibility timeout, four-day retention. Why: the queue is the buffer. If the consumer is down, messages accumulate rather than being lost, and processing resumes where it stopped.
Audit queue
A second subscriber with a filter policy matching priority = high. Why: filtering happens at SNS, so this consumer is never invoked for messages it does not care about — cheaper and simpler than filtering in code.
Dead-letter queue
Receives anything the orders queue fails to process three times, retained 14 days. Why: without it, a message that can never succeed retries until it expires, consuming invocations and hiding the failure. The DLQ turns it into a visible, inspectable item.
Consumer function
Lambda with a 30-second timeout, invoked with a batch of one. Why: raising an exception is how a Lambda SQS consumer signals failure — returning normally deletes the message. The timeout must stay below the visibility timeout, or a second invocation can pick up work still in progress.
Event source mapping
Lambda's managed poller reads the queue and invokes the function. Why: the function never polls. This is also what deletes messages automatically on success, which is why forgetting to raise on failure silently loses data.
Queue policy
Allows sqs:SendMessage from the SNS service principal, conditioned on this topic's ARN. Why: SQS is not in a VPC — access is a resource policy question, not a routing one.

Data flow
1
A publisher calls sns:Publish once, with a priority message attribute. The call returns as soon as SNS has durably accepted it — the publisher never waits for any consumer.
2
SNS delivers to both subscribed queues, checking each subscription's filter policy first. A priority = low message reaches the orders queue but is never delivered to the audit queue at all.
3
Raw message delivery is on, so each queue receives the payload itself rather than SNS envelope JSON wrapped around it.
4
Lambda's managed poller reads one message and invokes the consumer. The message becomes invisible to other consumers for 60 seconds — it is not deleted, only hidden.
5
On success the handler returns and the poller deletes the message. On failure the handler raises, nothing is deleted, and the message becomes visible again when the visibility timeout expires.
6
Each receive increments ApproximateReceiveCount. When it exceeds maxReceiveCount of 3, SQS moves the message to the dead-letter queue instead of making it visible again.
7
The message now sits in the DLQ for up to 14 days, inspectable, with no further processing attempts and nothing blocked behind it.
Key decisions
How should several consumers receive the same event?
One queue that every consumer reads
Standard SQS delivers each message to one consumer. Two consumers reading one queue split the work, they do not each get a copy — a genuinely common misunderstanding.
The publisher writes to each queue directly
Works, but now the publisher knows every consumer. Adding one means changing and redeploying the publisher, which is precisely the coupling this pattern exists to remove.
SNS fan-out to one queue per consumer
Chosen. Each consumer owns a queue and therefore its own buffer, retries and dead-letter behaviour, and the publisher stays unaware of all of them.
What should happen to a message that can never succeed?
Retry until it expires
Four days of retries at the queue's default, burning invocations, filling logs, and — with a small batch — delaying every message behind it.
Catch the error and return normally
The message is deleted and the failure vanishes. The queue looks healthy and the data is simply gone, which is worse than an alarm.
Redrive to a DLQ after 3 attempts
Chosen. Transient failures still get retried; permanent ones are quarantined quickly and visibly. A CloudWatch alarm on the DLQ's depth is the standard companion.
At least once means design for duplicates A standard SQS queue guarantees delivery at least once, not exactly once — and a visibility timeout that expires while a consumer is still working will hand the same message to a second one. Consumers must therefore be idempotent: processing the same message twice must produce the same result as processing it once. FIFO queues offer exactly-once processing within a deduplication window, at the cost of much lower throughput and strict ordering you often do not need.
Security · scaling · reliability · cost
Data protection
The queue policy admits only the SNS service principal, conditioned on this specific topic ARN, so no other topic or account can enqueue. The consumer's role grants three actions on one queue. Messages are encrypted at rest by default.
Scaling
Standard SQS has effectively unlimited throughput. Lambda scales its pollers with queue depth automatically. The usual bottleneck is downstream — a function scaling to hundreds of concurrent executions against a database that cannot take it, which is what reserved concurrency exists to cap.
Failure modes
A consumer outage becomes a growing queue rather than lost data — the defining property of this pattern. The real risks are a poison message with no DLQ, a visibility timeout shorter than processing time causing duplicate work, and a consumer that swallows exceptions and deletes messages it never processed.
Cost levers
All three services bill per request and nothing at rest. Long polling (ReceiveMessageWaitTimeSeconds up to 20) cuts empty-receive charges substantially. Filtering at SNS avoids paying for invocations that would discard the message anyway.
Operational notes~12 min live
Deploy
Under two minutes. Nothing is provisioned; the stack is queues, a topic, a function and IAM.
Observe
Publish a high-priority message and watch it arrive in both queues. Publish a low-priority one and watch the audit queue stay empty — the filter policy is doing that, not the consumer.
Break
Publish a message containing poison. The logs show receive #1, #2, #3 about a minute apart, and then it appears in the dead-letter queue. Nothing behind it was blocked.
Destroy
Under a minute. Like Lab 04, this stack costs nothing at rest — it is destroyed for consistency, not economy.
Watch these three things
  1. ApproximateReceiveCount in the logs, climbing 1 → 2 → 3. That counter, not any timer, is what triggers the redrive.
  2. The gap between retries — it is the visibility timeout, not a backoff setting.
  3. The audit queue staying empty for low-priority messages. Filtering at the topic means that consumer was never invoked at all.
Red flag — don't Never set a Lambda consumer's timeout higher than the queue's visibility timeout. The message becomes visible again while the first invocation is still running, a second invocation picks it up, and the work happens twice — with no error anywhere to show it. The rule is: visibility timeout ≥ function timeout, conventionally six times it.

Deliberately absent. No FIFO queue: exactly-once processing and strict ordering cost throughput, and most workloads need neither. No EventBridge, which routes on content across many targets and is the better answer once routing rules grow beyond a filter policy. No Step Functions, which coordinate multi-step workflows where a queue only moves one message.

The distinction the exam keeps testing SNS pushes; SQS is pulled. SNS delivers to every subscriber immediately and keeps nothing if delivery fails without a DLQ. SQS holds messages until a consumer asks for them, which is what provides the buffer. "Fan out to several consumers" is SNS. "Absorb a spike" or "survive a consumer outage" is SQS. "Both" is this architecture.
