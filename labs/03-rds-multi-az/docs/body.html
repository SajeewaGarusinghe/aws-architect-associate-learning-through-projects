Labs 01 and 02 built stateless things — anything could be replaced by anything else. A database cannot. This lab is about what high availability means once you have state that must survive, and about the difference between a standby you can fail over to and a replica you can read from.

Scope In scope: Multi-AZ synchronous replication, what actually happens during a failover, DB subnet groups, encryption at rest, and RDS-managed credentials in Secrets Manager. Out of scope: read replicas (asynchronous, and a different problem), Aurora, and cross-region disaster recovery — Lab 08 covers that.

Reference architecture

01. One endpoint, two availability zones
In one line

Multi-AZ is not a scaling feature and the standby serves no traffic — it exists purely so that the primary can disappear without losing a committed transaction, and the application keeps using the same endpoint name throughout.

Context & requirements

What it must do

  • Survive the loss of an availability zone
  • Lose no committed transaction when it does
  • Keep the same connection string throughout
  • Never expose the database to the internet

How it must behave

  • No password in the template, in git, or in CloudFormation
  • Storage encrypted at rest
  • Reachable only from the client security group
  • Failover measurable, not assumed

Constraints

  • db.t3.micro, 20 GB gp3 — smallest Multi-AZ possible
  • CIDR 10.40.0.0/16
  • Creation takes 12–15 minutes, and the meter runs
  • Destroyed by a single delete-stack
High-level design
RDS PostgreSQL, Multi-AZ
A db.t3.micro primary in AZ a with a synchronously replicated standby in AZ b. Why: every commit is acknowledged only after it is durable in both zones, which is what makes a zero-data-loss failover possible. The standby accepts no connections at all.
DB subnet group
Names the private subnets in both availability zones. Why: RDS requires subnets in at least two AZs even for a single-AZ instance — that requirement is what makes converting to Multi-AZ later a simple modify rather than a migration.
The endpoint DNS name
A CNAME that resolves to whichever instance is currently primary. Why: failover works by repointing this record, not by moving an IP address. The application never learns that anything happened beyond a dropped connection it must retry.
Secrets Manager
Created and owned by RDS through ManageMasterUserPassword, with rotation managed for you. Why: the master password is generated by AWS and never passes through the template, the console, CloudFormation's stored parameters, or this repository.
Database security group
Inbound TCP 5432 whose source is the client's security group. Why: the same construct as Lab 02 — nothing else in the VPC can open a connection to the database, whatever address it happens to hold.
Client instance
A t3.micro in the public subnet with no inbound rules, reached through Session Manager. Why: something has to hold a connection open across the failover so it can be observed. It sits in the public subnet purely so the SSM agent can reach the control plane without paying for interface endpoints.
Private route table
Local route only — no 0.0.0.0/0, no NAT gateway. Why: a database should have no path to the internet and no need for one. PubliclyAccessible: false is a second, independent control saying the same thing.
Encryption & logs
StorageEncrypted: true using the default RDS KMS key, with PostgreSQL logs exported to CloudWatch. Why: encryption must be enabled at creation — you cannot encrypt an existing unencrypted instance in place, only restore a snapshot into a new encrypted one.

Data flow
1
The client calls GetSecretValue on one specific secret ARN — the instance role grants nothing wider — and receives the password RDS generated. The password has never existed in the template.
2
It resolves the endpoint DNS name, which returns the private address of the current primary in AZ a, and opens a connection on TCP 5432.
3
The database security group admits it because the source is the client's security group. Nothing else in the VPC could have opened that connection.
4
On every commit, the primary writes to its own storage and waits for the standby to acknowledge before returning success. That wait is the cost of Multi-AZ, and the reason failover loses nothing.
5
On failover: RDS promotes the standby in AZ b and updates the endpoint's DNS record to point at it. Existing connections are severed — the application must reconnect; nothing is transparent at the TCP level.
6
The client's next connection resolves the same name, receives a 10.40.12.x address instead of 10.40.11.x, and carries on. Typical total interruption: 60 to 120 seconds.
Key decisions
How should the master password be handled?
A CloudFormation parameter with NoEcho
Hides it in the console, but it still travels through the deployment pipeline, appears in whoever ran the deploy's shell history, and must be rotated by hand forever.
A secret created separately and referenced
Better — the value stays in Secrets Manager. But you own the rotation Lambda, and the initial value still has to come from somewhere.
ManageMasterUserPassword: true
Chosen. RDS generates the password, creates the secret, owns it, and rotates it. No human or template ever sees the value. This is the current best-practice answer.
Multi-AZ or a read replica?
Read replica
Asynchronous, can lag, serves read traffic, can live in another region, and must be manually promoted — during which it may be missing recent writes. It solves read scaling, not availability.
Multi-AZ standby
Chosen. Synchronous, serves nothing, same region, fails over automatically with no data loss. It solves availability, not scaling. The exam tests whether you know these are different problems.
The sentence to remember Multi-AZ is for availability; read replicas are for scale. The standby cannot be read from, adds no throughput, and roughly doubles the bill — you are buying a recovery time objective, nothing else. If a question asks how to reduce load on a busy primary, the answer is never Multi-AZ. If it asks how to survive an AZ failure without losing data, the answer is never a read replica.
Security · scaling · reliability · cost
Data protection
Encrypted at rest with KMS, in private subnets with no route to the internet, with PubliclyAccessible: false as a second independent control, and reachable only from one security group. Credentials are machine-generated and machine-rotated. Encryption must be chosen at creation — an existing unencrypted instance can only be encrypted by restoring a snapshot into a new one.
Scaling
Vertical only: change the instance class, which itself causes a failover. Storage can grow but never shrink, and autoscaling storage is available. For read scaling you add read replicas; for write scaling beyond one instance you need sharding or Aurora.
Failure modes
AZ loss, instance failure, storage failure and patching all trigger the same automatic failover, typically 60–120 seconds. Connections break every time — an application without connection retry logic will surface errors to users even though the database itself lost nothing. Maintenance windows cause this deliberately.
Cost levers
Multi-AZ doubles both instance and storage cost for capacity that serves no traffic. Development environments rarely justify it. Backups within the retention period are free up to the size of the database; snapshots beyond that bill per GB.
Operational notes~35 min live
Deploy
12–15 minutes, far longer than any previous lab, and the meter runs the whole time. RDS provisions the primary, then builds and synchronises the standby. Budget for this: it is most of the cost of the lab.
Observe
Confirm the endpoint resolves to a 10.40.11.x address, that the console shows a standby in the other AZ, and that the secret exists with a password neither of you has ever seen.
Break
Start dbwatch on the client, then force a failover. Watch the query loop error for around a minute and recover with the same endpoint name resolving to a different address. The Events tab narrates the promotion.
Destroy
One delete-stack, around 8 minutes — RDS must delete two instances and their automated backups. DeleteAutomatedBackups and a Delete deletion policy prevent a final snapshot being retained and billed.
Watch these three things
  1. inet_server_addr() in the query loop — the address changes from 10.40.11.x to 10.40.12.x while the hostname you connected to never does.
  2. How long the loop errors for. That interval is your real recovery time objective, and it is the number to quote when someone asks what Multi-AZ buys.
  3. The RDS Events tab, which logs the failover in plain language along with its cause.
Red flag — don't Never assume Multi-AZ makes failover invisible to the application. Every failover severs every open connection. An application without retry and reconnect logic will throw errors to users during a routine patch, and the database will be entirely healthy throughout. Multi-AZ protects your data; only the client protects the user experience.
