Disaster recovery is usually taught as four named strategies and a pair of acronyms. This lab builds the two mechanisms underneath them: the thing that moves traffic when something dies, and the thing that determines what you can get back afterwards. Everything else is a choice about how much to spend on each.

Scope In scope: Route 53 failover routing and health checks, TTL as a recovery-time floor, S3 versioning, DynamoDB point-in-time recovery, and how RTO and RPO map onto the four DR strategies. Out of scope: cross-region replication, AWS Backup, and Aurora Global Database.

Reference architecture

01. Moving traffic, and getting data back
In one line

Failover is a DNS answer changing, which means your recovery time can never be shorter than the TTL clients already cached — and your recovery point is decided long before the disaster, by whether versioning and point-in-time recovery were switched on.

Context & requirements

What it must do

  • Send traffic elsewhere when the primary fails
  • Return automatically when it recovers
  • Recover an object overwritten by mistake
  • Restore a table to a point before an error

How it must behave

  • Failover requires no human action
  • Detection within roughly 60 seconds
  • Recovery point measured in seconds, not days
  • Every claim observable with dig

Constraints

  • No domain owned — query the zone's own nameservers
  • No EC2, no VPC, single region
  • Under $0.002/hour
  • Destroyed by a single delete-stack
High-level design
Health check
HTTP, every 30 seconds, unhealthy after 2 consecutive failures. Why: checkers in many AWS regions request the path independently, so a single network problem near one checker cannot trigger a false failover.
Hosted zone
A public zone for a domain nobody owns. Why: it will never resolve through the public DNS hierarchy, but querying its assigned nameservers directly works — which is all that is needed to watch the answer change.
PRIMARY record
A failover record carrying the health check, answered while healthy. Why: only a failover record set uses a health check this way. Weighted and latency records use health checks to remove an endpoint from a pool, which is a different behaviour.
SECONDARY record
The same name, answered only when the primary is unhealthy, with no health check of its own. Why: there is nothing beyond it to fail over to — if the secondary is also down, Route 53 answers with it anyway.
60-second TTL
How long resolvers may cache the answer. Why: this is a floor on recovery time. A 24-hour TTL means some clients keep using a dead endpoint for a day no matter how fast Route 53 reacts.
Versioned bucket
S3 versioning with noncurrent versions expiring after a day. Why: versioning turns an overwrite or a delete into a recoverable event. Without it, an overwritten object is simply gone — there is no undo.
DynamoDB with PITR
Point-in-time recovery enabled — a single boolean. Why: it gives continuous backups for 35 days, restoring to any second. It is the difference between a recovery point of seconds and one of "whenever the last snapshot happened to run".

Data flow
1
Route 53 health checkers in several regions request the configured path every 30 seconds. A check is considered failed only when enough checkers agree, which is what prevents one bad network path causing a false failover.
2
A resolver queries the record name. While the health check passes, Route 53 answers with the PRIMARY value and the resolver caches it for 60 seconds.
3
The endpoint starts failing. After two consecutive failed checks — roughly 60 seconds — Route 53 marks the health check unhealthy.
4
New queries now receive the SECONDARY value. No record was edited and nobody was paged; the record set simply stopped being eligible to answer.
5
Clients that already resolved keep using the old answer until their cached TTL expires. Total observed recovery time is detection plus TTL — which is why the TTL is a floor you set in advance.
6
When the endpoint recovers, two consecutive passes mark it healthy and the primary answers again. Failback is automatic, and just as subject to caching.
7
Separately: every write to the versioned bucket keeps the previous version, and DynamoDB continuously captures changes so the table can be restored to any second in the last 35 days.
Key decisions
Which DR strategy does the budget justify?
Backup and restore
Cheapest by far — backups only, nothing running. Recovery takes hours to days because the environment must be built before data is restored. Correct for workloads that can genuinely be down that long.
Pilot light
Core data replicated continuously, servers switched off. Recovery in tens of minutes. Cheap, because you pay for storage but not compute.
Warm standby
A scaled-down but running copy, ready to take traffic and scale up. Recovery in minutes. This lab's failover records assume something is already running to fail over to.
Multi-site active/active
Both regions serve live traffic; recovery is effectively immediate. Roughly double the cost, and the hardest to build because data must be consistent in both directions.
What TTL should a failover record carry?
300 seconds or more
Fewer DNS queries and marginally lower Route 53 cost, but it adds up to five minutes to every recovery — during which a share of users are still being sent to the dead endpoint.
60 seconds
Chosen. The extra query volume is negligible, and it keeps the caching component of recovery time roughly equal to the detection component instead of dominating it. Lower than 60 buys little, because detection is the other half.
RTO and RPO, distinguished RTO is how long you are down: detection plus TTL plus whatever must be started. RPO is how much data you lose: the gap between the disaster and your last recoverable state. They are bought separately. Failover routing buys RTO and does nothing for RPO; versioning and point-in-time recovery buy RPO and do nothing for RTO. A question naming hours of acceptable downtime but zero data loss is describing a cheap RTO with an expensive RPO.
Security · scaling · reliability · cost
Data protection
The bucket blocks all public access and is encrypted; versioning means deletion writes a marker rather than destroying data. PITR protects the table against application bugs as much as against infrastructure failure — the common case is a bad deploy writing garbage, not a region disappearing.
Scaling
Route 53 is a global anycast service with a 100% availability SLA — the only AWS service that carries one. Nothing here needs capacity planning.
Failure modes
The dangerous ones are configuration, not outage: a TTL long enough to dominate recovery, a health check pointed at a path that stays up while the application is broken, and a secondary nobody ever tested. Failover to a standby that does not work is the most expensive failure in this lab's subject area.
Cost levers
Hosted zone $0.50/month, health check $0.50/month, queries about $0.40 per million. Versioning costs whatever the old versions occupy, which is why the lifecycle rule expires them. PITR adds roughly 20% to table storage cost.
Operational notes~15 min live
Deploy
Under two minutes, but the health check needs a further 60–90 seconds before it reports healthy. Querying immediately after deploy may return the secondary — that is the check still initialising, not a failure.
Observe
dig the record against the zone's own nameservers and get the primary address. Check the health check's status across its individual checker regions.
Break
Point the health check at a path that 404s. Within about 60 seconds the same query returns the secondary address — with no record edited. Restore the path and watch it fail back.
Destroy
Around two minutes. The bucket must be emptied including every version, and a versioned bucket is not empty just because the objects look deleted — delete markers are versions too.
Watch these three things
  1. The delay between breaking the check and the answer changing. That is your detection time, and adding the TTL gives the real recovery time.
  2. The health check's per-region observations. Some regions report failure before others — this is the consensus mechanism working.
  3. That no record was modified during failover. Both records exist the whole time; only eligibility changed.
Red flag — don't Never point a health check at a path that cannot fail with the application. A check on / served by a load balancer will keep passing while every database call behind it errors, so Route 53 never fails over and the outage simply continues. The health check must exercise the dependency you are actually worried about — and the same logic applies to the load balancer health checks in Lab 02.

Routing policies, in one line each Simple — one answer, no logic. Failover — active/passive, the one this lab builds. Weighted — split by proportion, for canaries and migrations. Latency — the region with the lowest latency for that user. Geolocation — by where the user is, for compliance and localisation. Geoproximity — by distance with an adjustable bias. Multivalue — up to eight healthy answers, a poor substitute for a load balancer. Matching the policy to the stated intent is a reliable source of exam marks.
