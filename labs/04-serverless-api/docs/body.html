Lab 04 — The Serverless API

An HTTP API, a function and a table — with no VPC, no subnets, no security groups, no instances, and no hourly charge of any kind.

Every previous lab billed by the hour whether or not anyone used it. A NAT gateway at $43 a month, a load balancer at $18, a Multi-AZ database at $57 — all charging steadily for the privilege of existing. This stack charges nothing until a request arrives, and that single difference reshapes every architectural decision in it.

Scope In scope: the request/compute/storage split without servers, Lambda execution roles and the initialisation phase, DynamoDB key design and why Query beats Scan, HTTP APIs versus REST APIs, and the per-request cost model. Out of scope: VPC-attached Lambdas, step functions, event sourcing, and provisioned concurrency.

Reference architecture

01. Three managed services and no network
In one line

There is no network diagram here because there is no network: the components are connected by IAM permissions and service integrations rather than by routes and security groups, and the entire architecture scales from zero to thousands of concurrent requests without anyone configuring capacity.

Context & requirements

What it must do

  • Accept HTTP requests on a public URL
  • Store and retrieve items durably
  • Scale to zero when unused
  • Show cold-start behaviour plainly

How it must behave

  • Function may touch exactly one table, four actions
  • No credentials anywhere — roles only
  • Reads use Query, never Scan
  • Logs retained one day, then discarded

Constraints

  • No VPC — attaching one would add cost and cold-start latency
  • Function code inline in the template, under 4 KB
  • On-demand billing on the table
  • Idle cost must be exactly zero
High-level design
API Gateway HTTP API
A public HTTPS endpoint with a $default route proxying everything to one function. Why: an HTTP API costs roughly 70% less than a REST API and adds less latency. REST APIs buy request validation, API keys with usage plans, WAF integration and private endpoints — none of which this needs.
Lambda function
Python 3.12, 256 MB, 10-second timeout, routing on method and path. Why: memory is the only performance dial — CPU and network scale with it — so 256 MB is often faster and cheaper than 128 MB, because the function finishes in less than half the time.
DynamoDB table
Partition key pk, sort key sk, on-demand billing. Why: on-demand charges per request and nothing at rest; provisioned capacity would bill around the clock. The composite key lets one Query return recent items in order without reading the whole table.
Execution role
Four DynamoDB actions on one table ARN, plus the managed basic-execution policy for logs. Why: the function holds no credentials — it assumes this role and receives temporary keys. Removing one action from this policy is the lab's failure injection.
Resource policy
A lambda:InvokeFunction permission granting the API Gateway service principal access, scoped to this one API's ARN. Why: this is what connects the API to the function. There is no network path between them — the relationship is entirely a pair of IAM statements.
CloudWatch log group
Created explicitly with one-day retention. Why: Lambda creates a log group implicitly on first invocation with never expire retention, which quietly accumulates cost forever. Declaring it in the template is how you control that.

Data flow
1
A client sends POST /notes to the API's HTTPS endpoint. TLS terminates at API Gateway; there is no certificate to manage and no listener to configure.
2
The $default route matches. API Gateway calls lambda:InvokeFunction, which succeeds because the function's resource policy names the API Gateway service principal and this API's ARN.
3
If no warm environment exists, Lambda creates one: downloads the code, starts the runtime and executes everything outside the handler — including the boto3 client. This is the cold start, and it happens once per environment, not per request.
4
The handler runs. It assumes the execution role automatically and receives temporary credentials; no access key exists anywhere in the code or configuration.
5
PutItem writes an item with partition key note and a timestamp-ordered sort key. DynamoDB replicates it across three availability zones before acknowledging.
6
A later GET /notes issues a Query on the partition key with ScanIndexForward: false, returning the 25 most recent items. It reads only that partition — a Scan would read every item in the table and bill accordingly.
7
Anything printed goes to CloudWatch Logs asynchronously. During the failure injection this is where the AccessDeniedException appears, naming the exact action and resource that was denied.
Key decisions
HTTP API or REST API?
REST API
The older, fuller product: request/response transformation, API keys with usage plans, per-method throttling, WAF integration, private endpoints, and caching. Roughly 3.5× the price per million requests and measurably more latency.
HTTP API
Chosen. Cheaper, faster, simpler, with native JWT authorisation — and everything this architecture actually uses. Reach for REST only when you need one of the features above; on the exam, API keys, usage plans and request validation all point to REST.
How should the table be read?
Scan with a filter expression
Reads every item in the table and then discards the non-matching ones — and you are billed for everything read, not for what comes back. Cost and latency grow with total table size forever.
Query on the partition key
Chosen. Reads only the matching partition, returns items already sorted by the sort key, and costs the same whether the table holds a thousand items or a billion. If your access pattern needs a different key, add a global secondary index — never reach for Scan.
Where the cost model changes everything In Labs 01–03, the architectural question was "how little can I leave running?" Here it is "how few requests can I serve?" — and the answer to idle is genuinely zero. That is why serverless dominates exam questions containing the words unpredictable, spiky, intermittent or infrequent traffic. The corollary matters too: at steady high volume, provisioned capacity and EC2 become cheaper again, which is why "always-on, predictable load" points back the other way.
Security · scaling · reliability · cost
Data protection
No long-lived credentials exist: the function assumes a role and gets temporary keys. Its policy names four actions on one table ARN rather than dynamodb:* on *. DynamoDB encrypts at rest by default. The API is public and unauthenticated — the one real weakness, and deliberate, so the URL can be opened in a browser.
Scaling
Nothing to configure. Lambda scales concurrent executions automatically to an account limit of 1,000 by default; DynamoDB on-demand absorbs traffic changes without a capacity setting. The scaling risk is the reverse of usual: a runaway loop scales up and bills for it, which is what reserved concurrency exists to cap.
Failure modes
All three services are regional and multi-AZ by default, so there is no availability zone to lose. Realistic failures are throttling (429 when concurrency is exhausted), timeouts at 10 seconds, and IAM denials. Blast radius is one function — nothing else in the account is affected.
Cost levers
Idle is free. Under load, the levers are memory size (more memory can cost less overall by finishing sooner), avoiding Scan, and log retention — the quiet one, since a default log group keeps data forever. Ten thousand requests through this stack costs under one cent.
Operational notes~15 min live
Deploy
Under two minutes — the fastest lab by far, because nothing has to be provisioned. There is no capacity to allocate, so creation is almost entirely control-plane record-keeping.
Observe
Call the root URL twice in quick succession and compare cold_start_age_seconds. The first call pays the initialisation cost; the second reuses the environment and is markedly faster.
Break
Remove dynamodb:Query from the execution role in the console. GET /notes immediately returns 500 while POST /notes still works — because only one action was denied. CloudWatch Logs names the action and resource exactly.
Destroy
Under a minute. Strictly speaking you could leave this stack running — it would cost nothing. It is destroyed anyway, for the same reason every lab is: the account returns to a known baseline.
Watch these three things
  1. cold_start_age_seconds across repeated calls — it shows you exactly when a new execution environment was created rather than reused.
  2. The AccessDeniedException message during the failure injection. It names the action, the resource and the role, and reading these fluently is a genuinely useful skill.
  3. The absence of an entire category of thing. No subnets, no route tables, no health checks, no instances to patch — and the architecture is still highly available.
Red flag — don't Never let a Lambda log group keep its implicit default. If the function is invoked before the log group is declared, Lambda creates one with retention set to never expire, and it accumulates charges silently for the life of the account. Declaring the log group in the template with an explicit retention — as this stack does — is the fix. The same trap catches Scan on a table that was small when the code was written.

Deliberately absent. No authentication, so the URL opens in a browser — production would add a JWT authorizer or IAM authorisation. No custom domain or certificate. No VPC attachment: Lambda in a VPC is only needed to reach private resources such as the Lab 03 database, and it adds cost and complexity without adding security here. No provisioned concurrency, which fixes cold starts at the price of paying hourly — which would undo the one property this lab exists to demonstrate.

The exam's framing Serverless is not automatically the right answer. It wins decisively for spiky, unpredictable or infrequent workloads, and for teams who want no servers to patch. It loses for sustained high-volume compute, for workloads needing more than 15 minutes per execution, and for anything requiring specific hardware. Read the question for the traffic pattern before choosing.
