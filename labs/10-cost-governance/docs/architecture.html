Nine labs have been created and destroyed in this account. This one turns on the services that would have told you about it — and then reads back the record of everything the earlier labs did. It is the only lab whose value comes from the history that already exists.

Scope In scope: CloudTrail versus Config and what each actually answers, log file validation, Config rules and compliance, and budgets with actual versus forecasted alerts. Out of scope: Cost Explorer (not enabled on this account), Organizations and consolidated billing, Savings Plans, and Trusted Advisor.

Reference architecture

01. Three services, three different questions
In one line

CloudTrail answers who did this and when, Config answers what does this look like now and is that allowed, and a budget answers is this going to cost more than I agreed to — they are constantly confused with each other, and the exam relies on that.

Context & requirements

What it must do

  • Record every management API call in every region
  • Prove the log has not been altered
  • Flag a public bucket or an open SSH port
  • Warn before spend exceeds a threshold

How it must behave

  • Multi-region, or it misses calls made elsewhere
  • Config scoped to a few resource types, not all
  • Alerts on forecast, not only on actual
  • Alert address never committed to a public repo

Constraints

  • Cost Explorer is not enabled on this account
  • Config bills per configuration item recorded
  • Log retention one day — this is a lab
  • Budget requires a confirmed email
High-level design
CloudTrail trail
Multi-region, global service events included, log file validation on. Why: a single-region trail silently misses everything done elsewhere. Validation writes digest files so tampering is detectable — the difference between a log and evidence.
Audit bucket
One bucket serving both services, each under its own prefix, all public access blocked, objects expiring after a day. Why: both services need explicit bucket policy statements naming their service principals — neither can write without them, and that is the usual cause of a trail that silently records nothing.
Config recorder
Scoped to four resource types rather than everything. Why: Config bills per configuration item recorded. AllSupported: true in a busy account is a genuinely common and unexpected bill, and scoping is the lever.
Two managed rules
S3_BUCKET_PUBLIC_READ_PROHIBITED and INCOMING_SSH_DISABLED. Why: AWS writes and maintains the evaluation logic. Custom rules run your own Lambda and cost more to build and operate — reach for managed rules first.
Monthly budget
$5 ceiling with two notifications. Why: ACTUAL at 50% fires after the money is spent; FORECASTED at 100% fires before it is, based on projected trend. The forecast alert is the one that actually prevents a surprise.
Parameter file
The alert email lives in infra/params.json, which is gitignored. Why: this repository is public. A budget alert address is not a secret, but committing a personal email to a public repo is a habit worth not forming.

Data flow
1
Every management API call in the account — from the console, the CLI, or CloudFormation — is captured by CloudTrail, in every region because the trail is multi-region.
2
Events are written to the audit bucket under AWSLogs/, and digest files are written alongside so any later alteration is detectable.
3
Independently, the last 90 days of events are queryable with lookup-events without reading the bucket at all — which is how you answer "who deleted that" in seconds.
4
Config records a configuration item whenever one of the four watched resource types is created, changed or deleted — a point-in-time snapshot of that resource's settings.
5
Each change triggers evaluation against the two rules. Results appear as COMPLIANT or NON_COMPLIANT per resource.
6
Meanwhile the budget tracks spend. At 50% of $5 actual, an email is sent. Separately, if the month's forecast exceeds $5, an email is sent before the money is spent.
7
The subscription must be confirmed from the inbox before any alert is delivered — an unconfirmed budget alert is silently useless.
Key decisions
Which service answers "why is this bucket public?"
CloudTrail alone
Tells you who called PutBucketPolicy and when — but you must already suspect the bucket, and you must search. It cannot tell you which buckets are public right now.
Config alone
Tells you the bucket is non-compliant now, and shows its configuration history — but not which principal made the change or from which IP.
Both, and they are complementary
Chosen. Config finds it; CloudTrail explains it. The exam habitually offers one when the question needs the other — read for whether it asks about state or about an action.
Which budget alert actually prevents overspend?
ACTUAL at 100%
Fires when the budget is already fully spent. Useful as a record, useless as a warning.
ACTUAL at 50% only
An earlier warning, but it says nothing about trajectory — 50% on the 2nd of the month is alarming, on the 28th it is fine.
FORECASTED at 100%, plus ACTUAL at 50%
Chosen. The forecast projects the month's trend and warns before the threshold is crossed, which is the only alert that gives time to act. The actual alert is the backstop for a sudden spike the forecast has not caught up with.
The distinction in one line CloudTrail is a ledger of actions. Config is an inventory of states. Any question containing "who", "when", "which user" or "from what IP" is CloudTrail. Any question containing "which resources are", "is it compliant", "how was it configured last Tuesday" is Config. Add CloudWatch as the third: it records metrics and logs about behaviour — how busy, how slow, how many errors — which is a third question again.
Security · scaling · reliability · cost
Data protection
The audit bucket blocks all public access and is encrypted. Log file validation means tampering is detectable. In a real environment this bucket belongs in a separate account that the audited account cannot write over — an attacker's first move is deleting the trail.
Scaling
Both services are account-wide and managed. The scaling concern is cost, not capacity: Config's volume grows with how many resource types you record and how often they change.
Failure modes
The characteristic failure is silence. A trail whose bucket policy is wrong records nothing and raises no error. A budget whose email was never confirmed sends nothing. Both look configured and neither works — which is why the console tour verifies delivery rather than trusting the resource exists.
Cost levers
The first copy of management events is free; a second trail bills. Data events — every S3 object read, every Lambda invoke — are charged per event and are the usual cause of a shock CloudTrail bill. For Config, scope the recorder. Budgets are free for the first two.
Operational notes~20 min live
Deploy
2–3 minutes. Requires infra/params.json with your email — the template has no default, deliberately. Confirm the subscription from your inbox or no alert will ever arrive.
Observe
Query CloudTrail for the last 90 days and read back the history of labs 01–09 — every CreateStack, every DeleteStack, every NAT gateway created and destroyed. This is the only lab that can show you the others.
Break
Create a security group allowing 0.0.0.0/0 on port 22. Config marks it NON_COMPLIANT within minutes; CloudTrail shows who created it. Two services, two halves of the answer.
Destroy
3–4 minutes. The recorder must stop before the delivery channel can go, and the bucket must be emptied. Consider keeping the budget — it is free and it protects every future lab.
Watch these three things
  1. Your own history in lookup-events. Nine labs of evidence were being recorded by the default event history before this trail existed.
  2. The delay before Config reports compliance. It is minutes, not seconds — Config is for governance, not for real-time prevention.
  3. Whether the budget email actually arrives. An unconfirmed subscription is the most common reason a budget alert never fires.
Red flag — don't Never enable CloudTrail data events across all S3 buckets without thinking. Management events are free and low-volume; data events log every single object-level operation, and on a busy bucket that is millions of events a day at $0.10 per hundred thousand. It is one of the fastest ways to turn a governance improvement into a five-figure surprise.

Deliberately absent. Cost Explorer is not enabled on this account, which is why every lab in this curriculum estimates cost from published rates instead of querying actual spend — worth knowing that enabling it is free, takes 24 hours to populate, and that its API calls cost $0.01 each. No Organizations or consolidated billing, which is where service control policies and volume discounts live. No Savings Plans or Reserved Instances: both trade commitment for discount, and both are answers to "predictable steady-state usage", never to "unpredictable spiky load". No Trusted Advisor, whose full check set needs a Business support plan.

The last word on cost, after ten labs The cheapest architecture in this curriculum was Lab 04 at exactly zero per hour idle. The most expensive was Lab 03 at $0.078, most of which bought a standby serving no traffic. The single largest avoidable line item anywhere was Lab 01's NAT gateway — $43 a month to pass packets nobody was sending. Cost optimisation on the exam is rarely about choosing a smaller instance. It is about noticing which components charge by the hour whether or not anyone uses them, and removing the ones that do not need to.
